# Feature Specification: news: 데일리 기술 뉴스 픽

**Feature Branch**: `001-news-daily-digest`

**Created**: 2026-10-24

**Status**: Draft

**Input**: User description: "news: 매일 오전 8시(KST)에 AWS What's New, AWS 블로그, AWS Machine Learning 블로그,
Hacker News, 그리고 AI 에이전트 관련 기술 블로그 등의 RSS를 수집하고, 그중 가장 중요한 글 1개를 골라
Slack 채널에 한국어로 게시한다. (게시 형식: 주제/내용/나에게 적용할 점/원문 링크, 관심 분야 기반 선정,
인프라·AI 에이전트 주제 균형, 중복 게시 금지, 새 글 없음·수집 실패 시 테스트 채널에 오류 알림)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 매일 아침 가장 중요한 글 1개 받기 (Priority: P1)

DevOps 취업을 준비하는 사용자는 매일 오전 8시(KST)에 Slack 채널에서 여러 기술 소식 출처 중
자신의 관심 분야에 가장 중요한 글 1개를 한국어 요약으로 받는다. 요약에는 실무나 학습에 바로
적용할 수 있는 포인트가 함께 담겨 있어, 원문을 다 읽지 않아도 핵심을 파악하고 필요하면 원문 링크로 이동한다.

**Why this priority**: 이 기능의 핵심 가치다. 이것만 동작해도 매일 정보를 직접 찾아보는 시간을 줄여 준다.

**Independent Test**: 출처 목록에 새 글이 있는 상태에서 실행하면, 정상 채널에 정해진 형식의 게시물
1건이 올라오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 등록된 출처들에 아직 게시하지 않은 새 글이 여러 개 있음, **When** 매일 오전 8시(KST) 실행이 시작됨,
   **Then** 정상 채널에 게시물이 정확히 1건 올라오고, 그 안에 주제(한 줄), 내용(3~5줄 요약),
   나에게 적용할 점(1~2개), 원문 링크가 모두 한국어로(링크 제외) 포함된다.
2. **Given** 새 글 후보 중 관심 분야(AWS, Docker, Kubernetes, CI/CD, 모니터링, AI 에이전트, DevOps 취업)와
   직접 관련된 신규 서비스 발표와 관련 없는 일반 기사가 섞여 있음, **When** 글을 선정함,
   **Then** 관심 분야와 관련된 글이 선정된다.
3. **Given** 원문이 영어로 작성된 글이 선정됨, **When** 게시물을 만듦, **Then** 주제·내용·적용할 점은 한국어로 작성되고
   원문 링크는 원래 URL 그대로 포함된다.

---

### User Story 2 - 중복 없이 주제가 고르게 섞인 게시 (Priority: P2)

사용자는 같은 글을 두 번 받지 않으며, 며칠 동안 받은 게시물이 인프라 주제나 AI 에이전트 주제 한쪽으로
치우치지 않고 번갈아 섞여 있기를 기대한다.

**Why this priority**: 중복이나 편중이 생기면 매일 받는 가치가 크게 떨어지지만, P1이 먼저 동작해야 의미가 있다.

**Independent Test**: 게시 이력을 미리 채워 둔 상태에서 실행해, 이력에 있는 글이 다시 선정되지 않는지,
최근 게시 주제와 반대 분류의 글이 우선되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 오늘 가장 점수가 높은 글이 과거에 이미 게시된 글임, **When** 글을 선정함,
   **Then** 그 글은 제외되고 다음 순위의 미게시 글이 선정된다.
2. **Given** 같은 글이 서로 다른 출처(예: AWS 블로그와 Hacker News)에 동시에 올라옴, **When** 그중 하나가 이미 게시됨,
   **Then** 다른 출처의 같은 글도 중복으로 보고 게시하지 않는다.
3. **Given** 최근 연속 2회 게시가 모두 인프라 주제였음, **When** 인프라 글과 AI 에이전트 글의 중요도가 비슷함,
   **Then** AI 에이전트 주제 글이 선정된다.
4. **Given** 같은 날 실행이 두 번 일어남(재실행 등), **When** 두 번째 실행이 시작됨,
   **Then** 정상 채널에 같은 날 두 번째 게시물이 올라가지 않는다.

---

### User Story 3 - 실패 시 테스트 채널로 알림 (Priority: P3)

사용자(운영자)는 새 글이 없거나 수집에 실패하면 정상 채널이 아닌 테스트 채널에서 오류 알림을 받아,
정상 채널이 잘못된 게시물로 오염되지 않은 상태에서 문제를 파악할 수 있다.

**Why this priority**: 운영 안정성에 필요하지만, 정상 경로가 먼저 동작해야 의미가 있다.

**Independent Test**: 모든 출처를 사용할 수 없게 하거나 새 글이 없는 상태로 실행해, 테스트 채널에만
알림이 오고 정상 채널에는 아무것도 게시되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 모든 출처의 수집이 실패함, **When** 실행됨, **Then** 테스트 채널에 실패한 출처와 원인 요약이 담긴
   오류 알림이 1건 올라오고, 정상 채널에는 아무것도 게시되지 않는다.
2. **Given** 수집은 성공했지만 미게시 새 글이 하나도 없음, **When** 실행됨,
   **Then** 테스트 채널에 "새 글 없음" 알림이 올라오고 정상 채널에는 게시되지 않는다.
3. **Given** 일부 출처만 수집에 실패하고 나머지에서 후보 글을 얻음, **When** 실행됨,
   **Then** 정상 채널에는 정상적으로 1건이 게시되고, 테스트 채널에는 실패한 출처를 알리는 경고가 올라온다.
4. **Given** 요약 생성 또는 정상 채널 게시가 재시도 후에도 실패함, **When** 실행이 끝남,
   **Then** 테스트 채널에 오류 알림이 올라오고, 해당 글은 게시 이력에 "게시됨"으로 기록되지 않는다.

---

### Edge Cases

- 한 출처에서 같은 글의 제목이나 링크가 조금씩 바뀌어 다시 나타나는 경우(추적 파라미터 등):
  정규화한 링크를 기준으로 중복을 판단한다.
- 후보 글이 모두 관심 분야와 관련도가 매우 낮은 경우: 가장 높은 점수의 글을 게시하되, 관련도가 낮다는 사실을
  테스트 채널에 경고로 남긴다.
- 원문이 짧거나 본문 없이 제목·링크만 있는 경우(예: Hacker News 항목): 제공된 정보 범위 안에서만 요약하고,
  원문에 없는 사실을 지어내지 않는다.
- 실행당 비용 상한에 도달한 경우: 추가 처리를 멈추고, 게시하지 않은 채 테스트 채널에 알린다.
- 예정 시각에 실행되지 못한 경우(실행 환경 중단): 다음 실행 때 지난 기간의 미게시 글도 후보로 포함하되,
  게시는 하루 1건만 한다.
- 출처가 응답은 하지만 형식이 깨진 데이터를 주는 경우: 해당 출처를 수집 실패로 처리한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 MUST 매일 오전 8시(KST)에 자동으로 1회 실행된다(주말·공휴일 포함).
- **FR-002**: 시스템은 MUST 설정에 등록된 출처 목록에서 글을 수집한다. 초기 출처는 AWS What's New,
  AWS 블로그, AWS Machine Learning 블로그, Hacker News, AI 에이전트 관련 기술 블로그 묶음이다.
- **FR-003**: 사용자는 MUST 코드를 바꾸지 않고 설정만으로 출처를 추가·삭제할 수 있다.
- **FR-004**: 시스템은 MUST 각 출처를 "인프라" 또는 "AI 에이전트" 주제 분류로 구분하거나, 개별 글 단위로
  주제를 판정할 수 있어야 한다.
- **FR-005**: 시스템은 MUST 미게시 후보 글 중 정확히 1개를 선정하며, 판단 기준의 우선순위는
  (1) 사용자 관심 분야와의 관련도, (2) 실무 영향도(신규 서비스, 주요 기능 변경, 보안 이슈), (3) 학습 가치 순이다.
- **FR-006**: 사용자 관심 분야 목록은 MUST 설정으로 관리된다. 초기값은 클라우드 인프라(AWS), Docker, Kubernetes,
  CI/CD, 모니터링, AI 에이전트(LLM 활용, 에이전트 프레임워크, MCP, 자동화), DevOps 취업 준비다.
- **FR-007**: 시스템은 MUST 최근 게시 이력을 참고해 주제가 편중되지 않게 한다. 최근 연속 2회가 같은 주제
  분류였다면, 중요도가 비슷한 경우 다른 분류의 글을 우선한다. 단, 보안 이슈처럼 실무 영향도가 확연히 높은 글은
  예외로 선정할 수 있다.
- **FR-008**: 시스템은 MUST 이미 게시한 글을 다시 게시하지 않는다. 중복 판단은 정규화된 원문 링크를 기준으로 하며,
  서로 다른 출처에 올라온 같은 원문도 중복으로 본다.
- **FR-009**: 시스템은 MUST 게시 이력(글 식별자, 제목, 링크, 주제 분류, 게시 일시)을 실행 사이에도 유지되도록 저장한다.
- **FR-010**: 게시물은 MUST 다음 형식을 따른다: 주제(한 줄 제목), 내용(핵심 3~5줄 요약),
  나에게 적용할 점(관심 분야와 연결된 실무·학습 적용 기술 또는 아이디어 1~2개), 원문 링크.
- **FR-011**: 게시물의 주제·내용·적용할 점은 MUST 한국어로 작성하며, 원문에 없는 사실을 추가해서는 MUST NOT 한다.
- **FR-012**: 시스템은 MUST 정상 채널에 하루 최대 1건만 게시한다. 같은 날 재실행해도 추가로 게시하지 않는다.
- **FR-013**: 모든 출처의 수집이 실패하거나 미게시 새 글이 없으면, 시스템은 MUST 테스트 채널에 오류 알림을 남기고
  정상 채널에는 게시하지 MUST NOT 한다.
- **FR-014**: 일부 출처만 수집에 실패한 경우, 시스템은 MUST 나머지 출처로 정상 게시를 진행하고 테스트 채널에
  실패한 출처 목록을 경고로 남긴다.
- **FR-015**: 외부 출처 수집, 요약 생성, 채널 게시가 실패하면 시스템은 MUST 재시도하고, 재시도가 모두 소진되면
  실패를 기록하고 테스트 채널에 알린다(헌법 원칙 V).
- **FR-016**: 시스템은 MUST 실행 1회당 요약·선정에 쓰는 언어 모델 호출 횟수를 최소화하고, 실행당 비용 상한을
  설정으로 관리한다. 상한에 도달하면 처리를 멈추고 테스트 채널에 알린다(헌법 news-digest 원칙).
- **FR-017**: 정상 채널, 테스트 채널, 외부 서비스 인증 정보는 MUST 환경변수로만 받는다(헌법 원칙 IV).
- **FR-018**: 게시가 확실히 성공한 경우에만 MUST 해당 글을 게시 이력에 "게시됨"으로 기록한다.
- **FR-019**: 오류 알림에는 MUST 실행 시각, 실패 단계(수집/선정/요약/게시), 실패한 출처 또는 원인 요약이 포함된다.
- **FR-020**: 사용자는 MUST 정상 채널에 게시하지 않고 결과를 확인할 수 있는 수동 실행 방법(예: 테스트 채널로만
  게시하는 모드)을 사용할 수 있어야 한다.

### Key Entities *(include if feature involves data)*

- **출처(Source)**: 수집 대상 피드. 이름, 피드 주소, 기본 주제 분류(인프라/AI 에이전트), 사용 여부.
- **후보 글(Article)**: 수집된 개별 글. 제목, 원문 링크(정규화된 형태 포함), 출처, 발행 일시, 본문 또는 요약 발췌, 주제 분류.
- **게시 이력(Post Record)**: 정상 채널에 게시된 글의 기록. 글 링크, 제목, 주제 분류, 게시 일시, 게시 날짜(KST).
- **게시물(Digest Post)**: 채널에 올라가는 메시지. 주제, 내용(3~5줄), 나에게 적용할 점(1~2개), 원문 링크.
- **실행 결과(Run Result)**: 1회 실행의 결과. 실행 시각, 출처별 수집 성공·실패, 선정 결과, 사용 비용, 최종 상태(게시/알림/중단).
- **관심 분야 프로필(Interest Profile)**: 선정 기준이 되는 사용자 관심 분야 목록과 주제 분류 매핑.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 30일 운영 기간 동안, 새 글이 존재한 날의 95% 이상에서 오전 8시(KST)부터 10분 이내에 정상 채널에 게시물이 올라온다.
- **SC-002**: 운영 기간 전체에서 같은 원문이 정상 채널에 두 번 게시되는 경우가 0건이다.
- **SC-003**: 하루에 정상 채널에 2건 이상 게시되는 경우가 0건이다.
- **SC-004**: 임의의 연속 7일 게시물 중 인프라 주제와 AI 에이전트 주제가 각각 최소 2건 이상 포함된다
  (해당 기간에 두 분류 모두 후보가 있었던 경우).
- **SC-005**: 모든 게시물이 4개 항목(주제, 3~5줄 내용, 1~2개의 적용할 점, 원문 링크)을 빠짐없이 갖춘다.
- **SC-006**: 수집 실패나 새 글 없음이 발생한 날의 100%에서 테스트 채널에 알림이 오고, 정상 채널에는 게시되지 않는다.
- **SC-007**: 사용자가 2주간 받은 게시물 중 80% 이상을 "내 관심 분야와 관련 있다"고 평가한다.
- **SC-008**: 실행당 언어 모델 사용 비용이 설정된 상한을 넘는 경우가 0건이다.

## Assumptions

- 사용자는 1명(본인)이며, 정상 채널과 테스트 채널은 이미 존재하고 게시 권한이 있다.
- "AI 에이전트 관련 기술 블로그"의 초기 목록은 plan 단계에서 정하고(예: 주요 LLM 제공사·에이전트 프레임워크
  블로그), 이후 설정으로 조정한다.
- "새 글"은 게시 이력에 없고, 최근 72시간 안에 발행된 글로 정의한다(실행이 누락된 날을 보완하기 위한 여유 포함).
