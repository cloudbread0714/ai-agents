### Session 2026-10-24

- Q: 예약 실행 지연으로 9시 게시가 늦어지면 어떻게 하나요? → A: cron을 앞당겨 08:40(KST, UTC 23:40)에 시작한다(analyze A1).
- Q: 전날 게시된 시나리오를 풀지 않았으면 다음 날은 어떻게 하나요? → A: 다음 날은 새 내용을 게시하고, 안 푼 것은 후보(밀린 문제)에 남긴다. (커리큘럼 개정 후에는 학습 계획의 다음 일차로 진행하고, 안 푼 시나리오는 "밀린 문제"로 함께 표시한다.)
- Q: 로컬에서 쌓인 진행 기록이 매일 9시 게시에 어떻게 반영되나요? → A: 진행 기록은 레포 안에 저장하고 게시는 원격 실행 환경(GitHub Actions)에서 한다. 커밋·푸시는 자동이 아니라 해결 확인 성공·포기·회고 저장 때 사용자에게 물어본 뒤 한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 6단계로 장애 하나를 끝까지 다루기 (Priority: P1)

인프라·서버 엔지니어 신입을 준비하는 사용자는 내 컴퓨터의 실습 환경에서 장애 시나리오 하나를 시작한다.
연결된 워밍업을 아직 안 했다면 필요한 진단 명령과 개념을 한 단계씩 따라 하며 익힌다. 워밍업을 마치면 시나리오가 열린다.

시나리오는 6단계로 진행된다.
1. **정상 상태 측정**: 장애를 넣기 전에 응답 시간, 오류율, CPU 등을 실제로 측정해 기록한다.
2. **장애 재현**: 시스템이 장애를 주입한다.
3. **증상 관찰**: 같은 측정을 다시 하고, 실습 컨테이너 안에서 진단 명령(`ss`, `top`, `vmstat`, `curl -v` 등)으로 무엇이 달라졌는지 본다.
4. **원인 분석**: 막히면 힌트를 한 단계씩 연다.
5. **해결**: 고친 뒤 검증을 요청하면 증상이 사라졌는지 자동 판정하고, 해결 후 지표를 다시 측정해 기록한다.
6. **재발 방지**: 회고에서 장애 보고서를 쓰고, 시나리오에 연결된 면접 질문에 답한다.

**Why this priority**: 이 기능의 핵심 학습 경험이다. 커리큘럼의 목표인 "측정값을 근거로 진단 절차를 설명하는 능력"을 이 흐름이 만든다.
Slack 알림 없이 이것만 있어도 혼자 실습할 수 있다.

**Independent Test**: 빈 진행 기록에서 #3(연결 거부) 시나리오를 골라 다음 순서로 끝까지 진행되고, 보고서 파일이 저장되는지 확인한다.
1. 워밍업 완료
2. 정상 상태 측정
3. 장애 재현
4. 장애 상태 측정
5. 실습 컨테이너에서 `ss -lntp` 실행
6. 수정 후 검증
7. 해결 후 자동 측정
8. 보고서 작성(면접 질문 답변 포함)
9. 원복

**Acceptance Scenarios**:

1. **Given** 시나리오의 연결 워밍업이 미완료임, **When** 시나리오를 시작하려 함, **Then** 시나리오는 열리지 않고 남은 워밍업과 시작 방법이 안내된다.
2. **Given** 워밍업을 모두 마쳤음, **When** 시나리오를 시작함, **Then** 장애는 아직 주입되지 않고, 정상 상태를 먼저 측정하라는 안내가 나온다.
3. **Given** 정상 상태 측정을 아직 기록하지 않았음, **When** 장애 재현을 요청함, **Then** 장애가 주입되지 않고 측정을 먼저 하라고 안내한다.
4. **Given** 정상 상태 측정이 기록됨, **When** 장애 재현을 요청함, **Then** 장애가 주입되고 사용자에게는 증상만 보인다(원인은 보이지 않는다).
5. **Given** 장애가 재현됨, **When** 사용자가 대상 서비스를 지정해 진단 명령(예: `ss -ant`, `top -b -n 1`, `vmstat 1 5`)을 실행함, **Then** 명령이 그 서비스와 같은 네트워크·프로세스 공간을 보는 리눅스 실습 컨테이너 안에서 실행되고 결과가 보인다. 호스트(macOS)에 해당 명령이 없어도 된다.
6. **Given** 장애 상태 측정을 한 번도 하지 않았음, **When** 해결 검증을 요청함, **Then** 판정 전에 장애 상태를 먼저 측정하라고 안내한다.
7. **Given** 장애 상태 측정을 마치고 문제를 고쳤음, **When** 검증을 요청함, **Then** 증상이 사라졌는지 자동 판정하고, 성공이면 해결 후 지표를 같은 방법으로 자동 측정해 기록한 뒤 원인 해설과 회고 안내를 보여 준다.
8. **Given** 해결(또는 포기)했음, **When** 회고를 시작함, **Then** 장애 보고서 초안이 `docs/reports/`에 만들어진다. 초안에는 측정 비교표(정상·장애·해결 후)가 실측값으로 채워져 있고, 나머지 항목은 사용자가 쓰도록 비어 있다.
9. **Given** 측정 기록에 없는 지표가 있음(예: 해결 후 CPU를 측정하지 못함), **When** 보고서 초안을 만듦, **Then** 그 칸은 "측정하지 않음"으로 표시되고 어떤 추정값도 채워지지 않는다.
10. **Given** 보고서에서 필수 항목(증상, 원인, 분석 과정, 해결 방법, 재발 방지, 면접 질문 답변)이 비어 있음, **When** 회고 완료를 요청함, **Then** 빈 항목을 알려 주고 완료로 기록하지 않는다.
11. **Given** 진행 중이거나 끝낸 시나리오가 있음, **When** 원복을 실행함, **Then** 실습 환경이 장애 주입 전의 깨끗한 상태로 돌아간다.

### User Story 2 - 매일 학습 계획에 맞춘 오늘의 주제 받기 (Priority: P2)

사용자는 매일 오전 9시(KST) 무렵 Slack 채널에서 학습 계획의 오늘 일차를 받는다.
메시지에는 다음이 담긴다.
- 오늘의 주제와 예상 소요 시간(60~90분)
- 오늘의 시나리오(또는 개념 미션)와 워밍업 상태
- 안 푼 시나리오 목록

계획은 네트워크·리눅스(1주) → 웹 서버·부하 테스트(2주) → DB·캐시(3주) 순서로 진행된다.
메시지에는 원인이나 힌트가 없다.

**Why this priority**: 커리큘럼 순서대로 꾸준히 실습하게 만드는 장치다. 실습 흐름(US1)이 있어야 의미가 있으므로 P2다.

**Independent Test**: 진행 기록과 게시 기록을 고정한 상태에서 게시를 실행해 다음을 확인한다.
- 학습 계획의 다음 일차가 선택된다.
- 메시지에 주제, 예상 시간, 시나리오, 워밍업 상태, 밀린 문제가 정해진 형식으로 담긴다.
- 원인·힌트 문구가 포함되지 않는다.

**Acceptance Scenarios**:

1. **Given** 아직 아무것도 게시하지 않았음, **When** 첫 게시가 실행됨, **Then** 1일 차(TCP/IP, OSI 7계층)의 주제와 개념 미션이 게시된다.
2. **Given** 어제 3일 차를 게시했음, **When** 오늘 게시가 실행됨, **Then** 4일 차(포트와 방화벽)의 주제와 연결 시나리오(#1, #4)가 게시된다. 주 시나리오는 1개이고, 두 번째는 "시간이 남으면"으로 표시된다.
3. **Given** 해결도 포기도 하지 않은 지난 시나리오가 3개 이상 쌓였음, **When** 게시가 실행됨, **Then** 새 일차로 넘어가지 않고 "따라잡기 날"로 가장 오래된 밀린 시나리오를 주 시나리오로 게시한다.
4. **Given** 오늘 일차에 연결된 시나리오를 이미 해결했음(예: 11일 차의 #6), **When** 게시됨, **Then** 같은 시나리오를 그날 주제의 관점으로 다시 보는 "복습"으로 표시한다.
5. **Given** 21일 차까지 모두 게시했음, **When** 다음 게시가 실행됨, **Then** 심화 시나리오(계획에 없는 시나리오)를 차례로 게시하고, 그것도 끝나면 복습 문제(포기한 것 우선, 그다음 힌트를 가장 많이 쓴 것)를 게시한다.
6. **Given** 오늘 이미 게시함, **When** 같은 날 게시가 다시 실행됨, **Then** 정상 채널에 중복 게시되지 않는다.
7. **Given** 시나리오 정의에 원인 해설·힌트·면접 질문 모범 답안 메모가 들어 있음, **When** 메시지를 만듦, **Then** 메시지에는 그 내용이 전혀 포함되지 않는다.

### User Story 3 - 일요일마다 한 주 학습 요약 받기 (Priority: P3)

사용자는 매주 일요일 Slack 채널에서 지난 한 주의 학습 요약을 받는다. 요약에는 다음이 담긴다.
- 학습 계획 진행도(N/21일 차)
- 해결·포기 수와 사용한 힌트 수
- 작성한 보고서 수와 아직 쓰지 않은 보고서
- 답한 면접 질문 수
- 약한 분야
- 밀린 문제

사용자는 이 요약을 보고 다음 주 학습량을 조절한다.

**Why this priority**: 동기 부여와 방향 설정을 돕지만, 실습과 매일 알림이 먼저 있어야 의미가 있다.

**Independent Test**: 한 주 동안의 진행 기록과 보고서 파일을 준비해 두고 요약을 실행하면, 모든 수치가 기록과 일치하게 게시되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이번 주에 시나리오 3개를 해결했고, 그중 보고서는 2개만 완료함, **When** 일요일 요약이 게시됨, **Then** 해결 3개, 보고서 2/3, 미작성 보고서 1개(시나리오 제목)가 표시된다.
2. **Given** 이번 주에 아무 활동도 없음, **When** 일요일 요약이 게시됨, **Then** 활동이 없었다는 안내와 다음 일차 주제가 표시된다(오류로 처리하지 않는다).
3. **Given** 일요일임, **When** 오전 9시 무렵 게시가 실행됨, **Then** 오늘의 일차와 주간 요약이 모두 게시된다.

---

### Edge Cases

- **측정 도구 실행 실패**(부하 도구 이미지를 받지 못함 등): 실패를 알리고 다시 시도하게 한다. 끝내 측정할 수 없으면 사용자가 "측정 생략"을 사유와 함께 선택할 수 있다. 이 경우 그 단계는 "측정 생략(사유)"으로 기록되고 값은 비워 둔다.
- **환경에서 수집할 수 없는 지표**(예: Kubernetes에서 컨테이너 CPU를 수집할 수 없음): 그 지표는 "측정 불가"로 기록한다. 추정값으로 채우지 않는다.
- **측정 중 장애 때문에 모든 요청이 실패함**: 오류율 100%와 실패한 요청 수를 실측값으로 기록한다. 응답 시간 통계는 성공 요청이 없으면 "해당 없음"으로 둔다.
- **진단 명령의 대상 서비스가 꺼져 있음**(장애로 종료된 컨테이너 등): 대상이 실행 중이 아니라고 알려 준다. 같은 네트워크의 다른 지점(프록시 컨테이너 등)에서 진단하는 방법을 안내한다.
- **보고서 파일을 사용자가 직접 지우거나 옮김**: 해당 시나리오는 "보고서 미작성"으로 다시 표시된다.
- **같은 시나리오를 다시 풀 때**: 새 시도의 보고서는 새 파일(날짜·시도 번호 포함)로 만든다. 이전 보고서는 덮어쓰지 않는다.
- **어제 게시된 시나리오를 풀지 않았을 때**: 오늘은 다음 일차로 진행한다. 안 푼 것은 "밀린 문제"로 표시한다(최대 3개). 3개 이상 쌓이면 따라잡기 날이 된다.
- **오늘의 시나리오가 게시될 때 다른 시나리오가 진행 중일 때**: 메시지에 진행 중인 시나리오가 있다고 표시하고, 끝내거나 원복한 뒤 시작하라고 안내한다.
- **진행 기록을 푸시하지 않은(거절 또는 실패) 채로 오전 9시가 될 때**: 마지막으로 푸시된 기록으로 선택한다. 그래서 이미 푼 문제가 밀린 문제로 다시 보일 수 있다.
- **실습 환경이 로컬 샌드박스가 아닌 곳**(원격 클러스터, 공유 환경)을 가리킬 때: 장애 주입, 측정, 진단, 원복을 모두 거부하고 이유를 알린다.
- **실습 환경 자체가 준비되지 않았을 때**: 시작 전에 무엇이 없는지와 준비 방법을 알려 준다. "로컬 샌드박스가 아님" 거부와 구분해서 안내한다.
- **이미 다른 미션이나 시나리오가 진행 중일 때 새로 시작하면**: 진행 중인 항목을 먼저 끝내거나 원복하라고 안내하고 시작하지 않는다.
- **원복을 두 번 연속 실행하거나 시작하지 않은 상태에서 원복할 때**: 오류 없이 깨끗한 상태를 유지한다.
- **유효하지 않은 시나리오 정의**: 다음 경우에는 그 시나리오를 시작·선택 대상에서 제외하고 오류를 알린다.
  - 연결 워밍업이 없거나 3개 이상임
  - 원복 절차가 없음
  - 면접 질문이 없거나 3개 이상임
  - 분야가 6개 중 하나가 아님
- **게시에 실패할 때**: 정상 채널에는 아무것도 올리지 않고 테스트 채널에 실패 알림을 남긴다.
- **사용자가 끝내 풀지 못할 때**: 포기를 선택할 수 있다. 포기하면 원인 해설을 보여 준 뒤 "포기"로 기록하고 회고(보고서)는 그대로 진행한다.

### Functional Requirements

**학습 분야와 콘텐츠 구성**

- **FR-001**: 모든 미션과 시나리오는 MUST 다음 6개 학습 분야 중 하나에 속한다.
  - ① 네트워크
  - ② 리눅스 서버
  - ③ 웹 서버와 소켓
  - ④ 데이터베이스와 캐시

- **FR-002**: 각 장애 시나리오는 MUST 다음 항목을 가진다.

  - 연결 워밍업 1~2개
  - 정상 상태 측정 방법(대상, 부하 수준, 시간). 측정 지표는 FR-016의 공통 세트를 모든 시나리오가 함께 쓴다
  - 장애 주입 방법, 해결 판정 조건, 원복 절차
  - 순서가 있는 힌트 3단계, 원인 해설
  - 연결 면접 질문 1~2개

- **FR-005**: 각 워밍업 미션은 MUST 하나의 분야에 속하고, 명령어와 개념 설명이 있는 단계들로 구성된다. 여러 시나리오가 같은 워밍업을 공유할 수 있다.
  워밍업 전체는 MUST 다음 진단 명령과 개념을 다룬다.
  - ① 네트워크: `curl -v`, `curl -w`(DNS·연결·응답 시간), `dig`, `nslookup`, `nc`, `ss -lntp`, `ss -s`, `ip addr`, `ip route`, `openssl s_client`(인증서), 웹사이트 접속 과정(TCP/IP·OSI 개념)
  - ② 리눅스 서버: `top`, `ps aux --sort`, Load Average, `free -h`, `vmstat 1`, `df -h`, `du -sh`, `ulimit -n`, `lsof`, 컨테이너 로그·재시작 확인
  - ③ 웹 서버와 소켓: Nginx 리버스 프록시 구조, `ss -ant`와 TCP 상태(ESTABLISHED, TIME_WAIT, CLOSE_WAIT), 502·504 구분
  - ④ 데이터베이스와 캐시: PostgreSQL 연결 수와 실행 중 쿼리 확인, `EXPLAIN`, `redis-cli`(INFO, TTL, keyspace hit/miss)
  - ⑤ 부하 분산(로컬 대체): Kubernetes Service·엔드포인트와 readiness 개념
  - ⑥ 모니터링과 장애 대응: 부하 도구로 응답 시간·p95·처리량·오류율 측정, 로그 읽기, 배포 롤아웃·롤백

**워밍업 진행**

- **FR-006**: 워밍업의 각 단계 완료 여부는 MUST 자동으로 판정한다. 판정은 실습 환경의 결과 상태를 확인하거나, 해당 명령을 실행해야만 알 수 있는 값을 사용자가 입력하는 방식으로 한다.
- **FR-007**: 모든 단계가 완료로 판정되면 MUST 그 워밍업을 완료로 기록한다. 완료한 워밍업은 다른 시나리오에서도 완료로 인정하고, 사용자가 원하면 다시 할 수 있다.

**시나리오 6단계 흐름**

- **FR-008**: 연결된 워밍업을 모두 완료하기 전에는 MUST 시나리오를 시작할 수 없고, 남은 워밍업을 안내한다.
- **FR-009 (1단계: 정상 상태 측정)**: 시나리오를 시작하면 MUST 장애를 주입하기 전에 정상 상태를 측정하게 한다. 정상 상태 측정(또는 FR-016의 측정 생략)이 기록되기 전에는 장애를 주입하지 않는다.
- **FR-010 (2단계: 장애 재현)**: 정상 상태가 기록된 뒤 사용자가 장애 재현을 요청하면 MUST 로컬 실습 환경에 장애를 주입하고 증상만 안내한다. 원인은 보여 주지 않는다.
- **FR-011 (3단계: 증상 관찰)**: 사용자는 MUST 장애 상태를 같은 방법으로 측정할 수 있다. 또 대상 서비스를 지정해 리눅스 진단 명령을 실행할 수 있다(FR-018).
- **FR-012 (4단계: 원인 분석)**: 사용자는 MUST 힌트를 정해진 순서대로 한 번에 하나씩 열 수 있다. 연 힌트 수는 시도별로 기록된다.
- **FR-013 (5단계: 해결)**: 검증 요청을 다음 순서로 처리한다.
  1. 장애 상태 측정(또는 측정 생략)이 기록되지 않았으면 MUST 먼저 측정하라고 안내하고 판정하지 않는다.
  2. 기록이 있으면 MUST 해결 판정 조건으로 증상이 사라졌는지 자동 판정한다.
  3. 실패면 무엇이 남았는지 알리지 않고 실패만 알린다.
  4. 성공이면 해결로 기록하고(해결 시각, 사용한 힌트 수), 정상 상태와 같은 방법으로 해결 후 지표를 자동 측정해 기록한 뒤 원인 해설과 회고 안내를 보여 준다.
- **FR-014 (6단계: 재발 방지·회고)**: 해결 또는 포기 뒤 회고를 시작하면 MUST 장애 보고서 초안을 `agents/troubleshoot-lab/docs/reports/`에 만든다.
  - 파일 이름: `<YYYY-MM-DD>-<시나리오 id>-<시도 번호>.md`
  - 형식: 커리큘럼의 장애 보고서 템플릿(FR-021)
- **FR-015**: 사용자는 MUST 포기를 선택할 수 있다. 포기하면 원인 해설을 보여 주고 "포기"로 기록하며, 회고(보고서)는 해결과 똑같이 진행한다.

**측정 (실측값 원칙)**

- **FR-016**: 측정은 MUST 다음을 기록한다. 모든 측정은 단계(정상·장애·해결 후)와 측정 시각을 함께 기록한다.
  - 부하 도구로 대상 엔드포인트에 정해진 부하를 주어 얻은 평균 응답 시간, p95 응답 시간, 초당 처리량, 오류율, 요청 수
  - 같은 시간 동안 대상 서비스의 CPU 사용률과 메모리 사용량
- **FR-017**: 측정 기록과 보고서에는 MUST 실제 측정 결과만 들어간다.
  - 수집하지 못한 지표는 "측정 불가", 사용자가 생략한 단계는 "측정 생략(사유)", 해당 값이 성립하지 않는 경우(성공 요청 0건의 응답 시간 등)는 "해당 없음"으로 표시한다.
  - 시스템은 어떤 경우에도 추정값·예상값·이전 값으로 빈칸을 채우지 않는다.
  - 사용자가 보고서에 측정값을 직접 고쳐 쓰는 것은 막지 않는다. 다만 자동으로 채운 측정표 옆에 "자동 측정 기록"임을 표시해 출처를 구분한다.
- **FR-018**: 부하 테스트 도구는 MUST k6를 사용하고, 사용자가 호스트에 따로 설치하지 않아도 실행되어야 한다.
  리눅스 진단 명령(`ss`, `top`, `vmstat`, `free`, `df`, `dig`, `curl -v`, `nc`, `ip`, `lsof`, `ulimit` 등)은 MUST 대상 서비스와 같은 네트워크·프로세스 공간을 보는 리눅스 실습 컨테이너 안에서 실행된다(호스트는 macOS).
  사용자는 단일 명령 실행과 대화형 쉘 둘 다 쓸 수 있다.
- **FR-019**: 각 시나리오의 측정 방법(대상 엔드포인트, 부하 수준, 시간)은 MUST 시나리오 정의에 고정되어 있다. 정상·장애·해결 후 측정은 같은 방법으로 수행되어 서로 비교할 수 있어야 한다.
  측정 1회는 1분 이내에 끝나야 한다(하루 학습 시간 안에 여러 번 측정할 수 있도록).

**장애 보고서와 면접 질문**

- **FR-020**: 보고서 초안은 MUST 다음을 미리 채운다.
  - 장애명(시나리오 제목)
  - 측정 비교표(지표 × 정상·장애·해결 후, FR-017 규칙)
  - 사용한 힌트 수
  - 시나리오의 면접 질문

  나머지 내용은 사용자가 쓰도록 빈 칸으로 둔다. 시스템은 원인·분석·해결 내용을 대신 써 넣지 않는다.
- **FR-021**: 보고서 형식은 MUST 다음 순서의 항목을 가진다.
  1. 장애명
  2. 증상
  3. 원인
  4. 분석 과정
  5. 해결 방법
  6. 재발 방지
  7. 검증 결과(측정 비교표 포함)
  8. 회고(잘한 점, 부족했던 점, 더 효율적인 진단 방법, 약점 개념 태그)
  9. 면접 질문 답변(연결 질문 1~2개와 사용자의 답)
- **FR-022**: 사용자가 회고 완료를 요청하면 MUST 보고서의 필수 항목(증상, 원인, 분석 과정, 해결 방법, 재발 방지, 면접 질문 답변)이 비어 있지 않은지 확인한다. 채워졌으면 "회고 완료"로 기록하고, 비어 있으면 빈 항목을 알린다.
- **FR-023**: 보고서는 MUST 레포에 저장되고, 진행 기록과 함께 커밋·푸시할지 사용자에게 묻는 대상에 포함된다(FR-035). 보고서에는 비밀값이나 개인정보를 쓰지 않도록 초안에 안내 문구를 둔다.

**진단 실행과 안전**

- **FR-024**: 장애 주입, 측정, 진단 명령 실행, 원복은 MUST 로컬 샌드박스에서만 수행한다. 시작 전에 대상이 로컬 샌드박스인지 확인하고, 아니면 거부한다.
- **FR-025**: 한 번에 MUST 미션이나 시나리오 중 1개만 진행 중일 수 있다.
- **FR-026**: 원복은 MUST 언제든 실행할 수 있고, 실습 환경을 장애 주입 전의 깨끗한 상태로 되돌린다. 여러 번 실행해도 결과가 같다. 원복은 측정 기록과 보고서를 지우지 않는다.
- **FR-027**: 부하 도구의 대상은 MUST 로컬 실습 환경의 엔드포인트로만 제한된다. 외부 주소로 부하를 보내지 않는다.

**매일 학습 계획 알림**

- **FR-028**: 시스템은 MUST 매일 오전 9시(KST) 무렵 학습 계획의 오늘 일차를 정상 채널에 게시한다. 예약 실행 지연을 감안해 실행은 08:40(KST)에 시작한다. 날짜와 요일은 KST 기준이다.
- **FR-029**: 학습 계획은 MUST 커리큘럼의 1~3주 차 21일을 그대로 따른다. 각 일차는 주제, 실습 내용, 연결 시나리오(없으면 개념 미션), 예상 소요 시간을 가진다.

  | 주 | 일차: 주제 (연결) |
  |----|-------------------|
  | 1주: 네트워크와 리눅스 | 1 TCP/IP·OSI(개념) · 2 TCP 연결과 소켓(#3) · 3 DNS·HTTP·HTTPS(#2) · 4 포트와 방화벽(#1, #4) · 5 리눅스 프로세스(#1) · 6 메모리와 디스크(#8, #9) · 7 종합(#1~#4 중 1개, FR-030 규칙 5) |
  | 2주: 웹 서버와 부하 테스트 | 8 Nginx·리버스 프록시(개념) · 9 502·504(#5, #6) · 10 CPU 과부하(#7) · 11 타임아웃(#6) · 12 TCP 상태(#10, #11) · 13 동시 요청·k6(#7) · 14 장애 종합 분석(#17) |
  | 3주: DB와 캐시 | 15 PostgreSQL 연결 구조(개념) · 16 커넥션 풀(#12) · 17 느린 쿼리(#19) · 18 Redis 기초(개념) · 19 Cache Hit/Miss(#13) · 20 캐시 만료(#14) · 21 종합 장애(#18, #20) |

- **FR-030**: 오늘의 일차는 MUST 다음 규칙으로 정한다. 같은 진행 기록·게시 기록·날짜에서는 항상 같은 결과를 낸다.
  1. 해결도 포기도 하지 않은 지난 시나리오(밀린 문제)가 3개 이상이면 "따라잡기 날"로 정한다. 새 일차로 넘어가지 않고, 가장 오래전에 게시된 밀린 시나리오를 주 항목으로 한다.
  2. 그렇지 않으면 마지막으로 게시한 일차의 다음 일차로 진행한다(처음이면 1일 차). 진행 여부는 게시 기준이다. 안 푼 시나리오는 밀린 문제로 남는다(Clarification Q1).
  3. 21일 차까지 게시했으면 심화 시나리오(FR-004 표의 "심화")를 표 순서대로 하나씩 게시한다. 그것도 끝나면 복습 문제를 게시한다. 복습은 포기한 것을 가장 오래전에 포기한 순으로 먼저, 그다음 해결한 것 중 힌트를 가장 많이 쓴 것(같으면 가장 오래전에 해결한 것)을 고른다.
  4. 전날과 같은 시나리오는 다른 후보가 있으면 주 항목으로 고르지 않는다.
  5. 종합 일차(7일 차처럼 여러 시나리오 중 하나를 고르는 날)는 후보 시나리오 중에서 주 항목 1개를 다음 순서로 고른다.
     1. 해결도 포기도 하지 않은 것 중 한 번도 게시하지 않은 것
     2. 해결도 포기도 하지 않은 것 중 가장 오래전에 게시한 것
     3. 그다음 포기한 것
     4. 그다음 사용한 힌트가 가장 많은 것
     5. 같으면 커리큘럼 번호 순

     두 번째 항목은 두지 않는다.
- **FR-031**: 일차 메시지는 MUST 다음 내용만 담는다. 원인 해설, 힌트, 태그, 면접 질문 모범 답안 메모는 MUST NOT 포함한다.
  - 일차 번호와 주차, 오늘의 주제, 예상 소요 시간
  - 주 항목: 시나리오(난이도, 분야, 증상, 시작 명령) 또는 개념 미션
  - 연결 시나리오가 2개인 날의 두 번째 항목: "시간이 남으면"으로 표시
  - 연결 워밍업 목록: 완료한 것은 "완료됨", 아니면 시작 방법
  - 밀린 문제 최대 3개(제목과 시작 명령)
  - 오늘 시나리오를 이미 해결했으면 "복습" 표시와 함께 그날의 실습 내용(커리큘럼의 실습 문구)을 "이번에는 이 관점으로" 안내
- **FR-032**: 하루 학습량은 MUST 60~90분 기준으로 맞춘다.
  - **계획 검증**: 각 일차의 주 항목과 연결 워밍업 전부(아무것도 완료하지 않은 상태 기준)의 예상 소요 시간 합이 60~90분이어야 한다. 종합 일차는 후보 각각이 이 범위여야 한다.
  - **게시 시점**: 이미 완료한 워밍업은 빼고 계산한다.
    - 90분을 넘으면 메시지에 예상 시간이 90분을 넘는다고 표시한다. 두 번째 시나리오는 늘 "시간이 남으면"이다.
    - 60분보다 적으면 남는 시간에 "시간이 남으면" 항목이나 밀린 문제를 하라고 안내한다. 하한 미달은 오류가 아니다.
- **FR-033**: 선택과 메시지 작성은 MUST LLM을 사용하지 않는다.
- **FR-034**: 하루에 MUST 정상 채널에 일차 메시지를 최대 1번만 게시한다. 같은 날 다시 실행되어도 중복 게시하지 않는다.

**진행 기록 동기화**

- **FR-035**: 진행 기록(워밍업 완료, 시나리오 시작·측정·해결·포기·회고 완료·원복, 힌트 사용)은 MUST 레포 안의 파일에 저장된다.
  다음 직후에는 MUST 사용자에게 진행 기록과 새 보고서 파일만 커밋·푸시할지 묻는다. 동의하면 그 파일들만 커밋·푸시한다.
  - 해결 확인 성공
  - 포기
  - 회고 완료

  매일 게시는 원격 실행 환경에서 레포의 최신 진행 기록을 읽어 선택한다.
- **FR-036**: 사용자가 거절하거나 푸시에 실패하면(오프라인, 기본 브랜치가 아닌 브랜치 등) MUST 기록은 로컬에 유지하고 이유를 알린다. 쌓인 변경은 다음 동의 때 함께 올라간다.
- **FR-037**: 진행 기록에는 MUST 학습 상태(식별자, 시각, 횟수, 결과, 측정값)만 담고 개인정보나 비밀값을 담지 않는다.

**주간 요약**

- **FR-038**: 시스템은 MUST 매주 일요일 오전 9시(KST) 무렵(일차 메시지와 같은 실행)에 이번 주(월요일 00:00부터 게시 시점까지, KST)의 학습 요약을 정상 채널에 게시한다.
  요약 항목은 다음과 같다.
  - 학습 계획 진행도(N/21일 차, 심화·복습 단계 표시)
  - 해결 수, 포기 수, 사용한 힌트 수
  - 회고 완료 수와 회고를 아직 하지 않은 시나리오 목록
  - 답한 면접 질문 수
  - 약한 분야
  - 밀린 문제 수
- **FR-039**: 약한 분야는 MUST 그 주에 시도한 시나리오의 대표 분야별로 (사용한 힌트 수 + (포기 수 + 해결 없이 원복한 시도 수) × 2)가 가장 큰 분야로 정한다.
  - 진행 중인 시도는 세지 않는다.
  - 같으면 해결 수가 적은 분야를, 그래도 같으면 ①→⑥ 순으로 고른다.
  - 시도가 없거나 모든 값이 0이면 "기록 없음"으로 표시한다.
  - 그 주에 활동이 없으면 오류 없이 활동이 없었다는 안내와 다음 일차 주제를 게시한다.

**실패 처리**

- **FR-040 (실패 알림)**: 게시에 실패하거나 시나리오 정의가 유효하지 않아 게시할 수 없으면 MUST 정상 채널에는 게시하지 않고 테스트 채널에 실패 단계와 원인을 알린다.

### Key Entities *(include if feature involves data)*

- **학습 분야(Field)**: 6개 고정 목록(①~⑥). 미션과 시나리오의 분류, 약한 분야 계산에 쓴다.
- **장애 시나리오(Scenario)**: 커리큘럼 번호, 식별자, 제목, 분야(대표 분야 + 관련 분야), 난이도, 증상, 예상 소요 시간, 연결 워밍업, 측정 방법(대상, 부하 수준, 시간, 지표), 장애 주입 방법, 해결 판정 조건, 원복 절차, 힌트 3단계, 원인 해설, 면접 질문 1~2개.
- **워밍업 미션(Warmup)**: 식별자, 제목, 분야, 예상 소요 시간, 단계 목록(설명, 따라 할 명령, 완료 판정 방법). 개념 일차의 "개념 미션"도 같은 형식이다.
- **학습 계획 일차(Plan Day)**: 일차 번호(1~21), 주차, 주제, 실습 내용, 연결 시나리오 또는 개념 미션, 예상 소요 시간.
- **측정 기록(Measurement)**: 시나리오, 시도, 단계(정상·장애·해결 후), 측정 시각, 지표별 값 또는 상태(측정 불가·측정 생략·해당 없음), 생략 사유.
- **진행 기록(Progress)**: 사용자 1명의 학습 상태. 다음을 담는다.
  - 워밍업 완료
  - 시나리오별 시도: 시작, 측정, 장애 주입, 힌트, 해결·포기·원복, 회고 완료, 보고서 경로
  - 현재 진행 중인 항목
- **장애 보고서(Report)**: 시도 하나에 대한 Markdown 문서(FR-021 형식). 레포의 `docs/reports/`에 저장된다.
- **게시 기록(Posting)**: 날짜(KST)별로 게시한 일차 번호(또는 따라잡기·심화·복습), 주 항목, 주간 요약 게시 여부. 다음 일차 계산과 중복 게시 방지에 쓴다.
- **주간 요약(Weekly Summary)**: 기간, 계획 진행도, 해결·포기·힌트 수, 회고 완료·미완료, 면접 질문 답변 수, 약한 분야, 밀린 문제 수.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 30일 동안 일차 메시지가 하루도 빠짐없이 08:40~09:30(KST) 사이에 정상 채널에 게시된다(실행 플랫폼 장애일 제외).
- **SC-002**: 게시된 모든 메시지에 원인 해설, 힌트, 태그, 면접 질문 모범 답안 메모 문구가 0건 포함된다.
- **SC-003**: 범위 안의 모든 시나리오(100%)가 다음 조건을 만족한다.
  - 6단계 흐름 정의(측정 방법, 주입, 판정, 원복, 힌트 3단계, 해설, 면접 질문 1~2개)를 갖춘다.
  - 원복 후 실습 환경이 장애 주입 전 상태와 같음이 검증된다.
- **SC-004**: 모든 측정 기록과 보고서 측정표의 칸은 실측값이거나 "측정 불가·측정 생략·해당 없음" 중 하나이며, 추정값으로 채워진 칸이 0개다.
- **SC-005**: 범위 안의 모든 시나리오에서 정상 상태 측정과 장애 상태 측정의 결과가 같은 지표에 대해 비교 가능하게 기록된다.
  그리고 각 시나리오의 장애 상태에서 다음 중 최소 1개가 정상 상태와 달라진다.
  - 오류율 5%p 이상 증가
  - 평균 또는 p95 응답 시간 1.5배 이상 차이(늘거나 줄거나. 캐시가 잘못 적용되면 오히려 빨라진다)
  - CPU 최대 사용률 20%p 이상 증가
  - 메모리 최대 사용량 1.3배 이상
  - 응답 시간이 "해당 없음"으로 바뀜(성공 요청 0건)
- **SC-006**: 측정 1회가 1분 안에 끝나고, 이미지 등이 준비된 상태에서 장애 재현 요청부터 증상 재현까지 3분 안에 끝난다.
- **SC-007**: 같은 진행 기록·게시 기록·날짜로 일차 선택을 반복하면 100% 같은 결과가 나온다.
- **SC-008**: 1~21일 차 각각에서 주 항목과 미완료 연결 워밍업의 예상 소요 시간 합이 60~90분 범위에 들어간다(두 번째 시나리오 제외).
- **SC-009**: 주간 요약의 해결·포기·힌트·회고 완료·면접 질문 답변 수가 진행 기록과 보고서 파일 상태와 100% 일치한다.
- **SC-010**: 사용자는 macOS 호스트에 k6나 리눅스 진단 도구를 따로 설치하지 않고도 모든 측정과 진단 명령을 실행할 수 있다.
- **SC-011**: 회고 완료로 기록된 모든 보고서에 필수 항목과 면접 질문 답변이 비어 있지 않다.

## Assumptions

- 사용자는 1명(레포 소유자)이다. 실습은 사용자의 macOS 컴퓨터에서 Docker 기반 로컬 환경(docker compose, kind)으로 하고, 이 도구들은 사용자가 미리 설치한다.
- 커리큘럼 기준 문서는 `agents/troubleshoot-lab/docs/curriculum.md`다. 학습 계획, 시나리오 목록, 보고서 템플릿, 면접 질문은 이 문서를 따른다. 문서가 바뀌면 스펙도 함께 개정한다.
- 실습 상호작용은 로컬 명령(Claude Code 슬래시 명령 포함)으로 하고, Slack은 알림을 받는 용도로만 쓴다. 상호작용에는 워밍업, 시작, 측정, 장애 재현, 진단, 힌트, 검증, 포기, 회고, 원복이 있다.
- 힌트, 원인 해설, 면접 질문은 시나리오마다 미리 작성해 둔다. 이 기능 전체에서 LLM으로 내용을 생성하거나 고르지 않는다. 보고서 본문은 사용자가 쓴다.
- k6와 리눅스 진단 도구는 컨테이너 이미지로 실행한다. 진단 컨테이너는 대상 컨테이너(또는 Pod)의 네트워크·프로세스 공간에 붙어서 실행된다.
- 부하 수준은 일반 노트북에서 실습 환경이 버틸 수 있는 정도로 시나리오마다 정한다. 측정의 목적은 성능 한계 측정이 아니라 정상·장애 상태의 비교다.
- 레포는 공개 상태이므로 진행 기록과 보고서도 공개된다. 보고서에 개인정보나 비밀값을 쓰지 않도록 초안에 안내한다.
- 한 주는 월요일 00:00 ~ 일요일 23:59(KST)이고, 일요일 요약은 그날 오전 9시 무렵까지의 기록을 기준으로 한다.
- Slack 정상 채널은 #daily-lab, 테스트 채널은 news-digest와 같은 #agent-test를 공유한다(같은 웹훅 설정을 재사용).
  개발 중 실행의 기본 게시 대상은 테스트 채널이고, 실행 옵션이나 환경 설정으로 정상 채널로 전환한다.
  매일·주간 정기 실행만 정상 채널로 게시하며, 실패 알림은 항상 테스트 채널로 보낸다.
- 이미 구현된 시나리오 9개와 미션 14개(Docker·Kubernetes·웹 분류)는 FR-004 표에 따라 새 분야로 재배치하고 6단계 흐름에 맞게 보완한다. 새 시나리오와 새 진단 미션은 추가로 작성한다.
