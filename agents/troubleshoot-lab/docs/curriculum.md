# Troubleshoot Lab 커리큘럼

인프라·서버·클라우드 엔지니어 신입 준비를 위한 장애 재현·분석·해결 실습 커리큘럼입니다.
트러블슈팅 에이전트(`agents/troubleshoot-lab/`)의 미션, 시나리오, 매일 알림, 회고는 이 문서를 기준으로 구성합니다.

---

## 1. 목표와 학습 원칙

### 목표

새로운 서비스를 무작정 늘리기보다, **리눅스·네트워크·서버 동작 원리를 이해하고 장애 대응을 반복 연습**한다.
면접에서 개념 설명을 넘어 **구체적인 진단 절차와 근거(측정값)** 를 제시할 수 있는 수준을 목표로 한다.

> "CPU가 높아서 서버가 느렸습니다"가 아니라
> "부하 테스트 중 CPU 사용률과 p95 응답 시간이 동시에 증가했고, 특정 연산을 최적화한 뒤 응답 시간이 개선되는 것을 확인했습니다"라고 말할 수 있어야 한다.

### 학습 원칙

- 모든 기술을 같은 깊이로 공부하지 않는다. **네트워크와 리눅스가 기반**이고, 그 위에서 웹 서버·DB·클라우드 장애를 이해한다.
- 개념을 읽으면 반드시 관련 명령어를 실행하고, **결과가 왜 그렇게 나오는지 설명**해 본다.
- 장애 대응에서 중요한 것은 재시작이 아니라 **원인 파악과 재발 방지**다.
- 측정값은 실제 테스트 결과로만 기록한다. **예상값을 실측값처럼 기록하지 않는다.**
- 문서는 처음부터 다 읽지 않는다. 당일 실습에 필요한 부분만 찾아 읽고 실습 결과와 연결한다.

### 장애 하나당 6단계 학습법

| 단계 | 내용 |
|---|---|
| 1. 정상 상태 확인 | 정상 상태의 CPU, 메모리, 네트워크 연결, 응답 시간을 측정하고 기록한다 |
| 2. 장애 재현 | 원인을 알고 있는 장애를 의도적으로 발생시킨다 (부하 요청, 포트 차단 등) |
| 3. 증상 관찰 | `top`, `ss`, `curl`, 로그 등으로 장애 시 어떤 변화가 나타나는지 확인한다 |
| 4. 원인 분석 | 오류 메시지에 그치지 않고, 어떤 자원이 부족하거나 어떤 요청 흐름이 막혔는지 설명한다 |
| 5. 해결 | 병목 제거, 설정 수정, 자원 사용 방식 개선 |
| 6. 재발 방지 | 모니터링 지표, 알림, 자동 복구, 타임아웃, 용량 계획 등 개선 방안을 정리한다 |

### 실습 환경 원칙

- 처음에는 AWS보다 **로컬 환경(Docker)** 에서 시작한다.
- macOS 호스트에는 `ss`, `free`, `vmstat`, `iostat` 등 리눅스 명령이 없거나 다르게 동작하므로, **진단 명령은 실습용 리눅스 컨테이너 안에서 실행**한다.
- 부하 테스트는 본인이 소유하거나 명시적으로 테스트 권한이 있는 로컬 환경에서만 진행한다.

### ① 네트워크

#### 핵심 개념

| 개념 | 반드시 답할 수 있어야 하는 질문 |
|---|---|
| OSI 7계층 | 각 계층은 어떤 역할을 하는가? |
| TCP/IP | TCP는 왜 연결을 설정하는가? |
| TCP 3-way handshake | SYN, SYN-ACK, ACK는 무엇인가? |
| TCP 연결 종료 | FIN과 RST는 어떻게 다른가? |
| 포트 | IP 주소가 같은데 여러 서비스에 접속할 수 있는 이유는? |
| 소켓 | IP 주소, 포트, 프로토콜은 연결 처리에서 어떤 역할을 하는가? |
| DNS | 도메인을 IP 주소로 변환하는 과정은? |
| HTTP/HTTPS | TCP 연결 이후 HTTP 요청은 어떻게 전달되는가? |
| TLS | HTTPS에서 암호화 연결은 어떻게 설정되는가? |
| NAT | 사설 IP를 사용하는 서버가 외부와 통신하는 원리는? |
| 라우팅 | 패킷은 목적지까지 어떤 경로로 전달되는가? |
| 서브넷 | CIDR, 서브넷 마스크, 네트워크 주소는 무엇인가? |
| 방화벽 | Security Group과 NACL은 어떤 차이가 있는가? |
| MTU | MTU 불일치가 통신 문제를 일으킬 수 있는 이유는? |

#### AWS와 연결해서 이해할 것

- TCP/IP ↔ AWS VPC
- 라우팅 테이블 ↔ 인터넷 게이트웨이
- NAT Gateway ↔ 프라이빗 서브넷
- Security Group ↔ NACL
- DNS ↔ Route 53
- TCP 연결 ↔ ALB
- HTTPS ↔ TLS 인증서

#### 진단 순서 예시: "웹 서버에 외부에서 접속할 수 없다"

무조건 Security Group부터 수정하지 않고, 아래 순서로 범위를 좁힌다.

1. 인스턴스(서버)가 정상적으로 실행 중인가?
2. 웹 서버 프로세스가 실행 중인가?
3. 웹 서버가 올바른 IP와 포트에서 리스닝 중인가?
4. 서버 내부에서 `curl localhost:80`이 성공하는가?
5. Security Group(방화벽)의 인바운드 규칙이 올바른가?
6. 서브넷의 라우팅 테이블과 인터넷 게이트웨이가 올바른가?
7. 클라이언트와 서버 사이에 추가적인 차단 요소가 있는가?

#### 진단 명령어

| 명령어 | 용도 |
|---|---|
| `ping` | ICMP 기반 연결성 확인 |
| `curl -v` | HTTP 요청 및 연결 과정 확인 |
| `curl -w` | DNS, 연결, 응답 시간 측정 |
| `dig` | DNS 조회 결과 확인 |
| `nslookup` | DNS 조회 |
| `ss -lntp` | TCP 리스닝 소켓 및 관련 프로세스 확인 |
| `ss -s` | 소켓 통계 확인 |
| `ip addr` | 네트워크 인터페이스와 IP 확인 |
| `ip route` | 라우팅 테이블 확인 |
| `traceroute` / `tracepath` | 네트워크 경로 진단 |
| `tcpdump` | 실제 네트워크 패킷 분석 |
| `nc` | TCP 연결 테스트 |
| `lsof -i` | 네트워크 소켓과 프로세스의 관계 확인 |

```bash
# HTTP 연결 과정을 상세히 확인
curl -v http://localhost:8000
# DNS 조회
dig example.com
# 리스닝 중인 TCP 포트 확인
sudo ss -lntp
# TCP 소켓 통계 확인
ss -s
# 특정 포트에 TCP 연결 시도
nc -vz 127.0.0.1 8000
# 네트워크 인터페이스 확인
ip addr
# 라우팅 테이블 확인
ip route
```

> `ping`이 실패한다고 TCP 연결도 반드시 실패하는 것은 아니다. 서버나 방화벽이 ICMP에 응답하지 않도록 설정되어 있을 수 있다.

### ② 리눅스 서버

명령어 암기보다 **서버 상태를 직접 분석**하는 연습이 중요하다.

#### CPU 사용량이 100%일 때

```bash
top
ps aux --sort=-%cpu | head
```

- 확인: CPU 사용률, CPU를 많이 쓰는 프로세스, Load Average, 프로세스 상태
- Load Average는 CPU 사용률과 같은 값이 아니다. 실행 대기 작업과 일부 I/O 대기가 반영되므로 **CPU 코어 수 및 다른 메트릭과 함께 해석**한다.

#### 메모리 부족

```bash
free -h
vmstat 1
```

- 확인: 사용 가능한 메모리, 스왑 사용량, 메모리 회수 활동, 프로세스 대기, 전반적인 부하
- 메모리가 부족하면 스왑 사용이 늘거나 프로세스가 **OOM Killer**에 의해 종료될 수 있다.

#### 디스크 용량 부족

```bash
df -h
du -sh /var/log/*
```

- 파일 시스템별 사용량과 로그 파일 점유를 확인한다. 권한과 디렉터리 구조에 따라 조회 범위를 조정한다.

#### 디스크 I/O 병목

```bash
iostat -xz 1   # sysstat 패키지 필요
```

- 디스크 처리량과 대기 시간을 관찰하며 I/O 병목 가능성을 확인한다.

#### 프로세스 및 서비스 장애

```bash
ps aux
systemctl status nginx
journalctl -u nginx --since "10 minutes ago"
```

명령어 결과를 보고 다음 질문에 답한다.

- 프로세스가 종료되었는가?
- 프로세스는 실행 중인데 응답하지 않는가?
- 로그에 오류가 기록되었는가?
- CPU, 메모리, 디스크 중 어느 자원이 병목인가?
- 재시작하면 일시적으로 해결되지만 다시 장애가 발생하는가?

> 컨테이너 환경에서는 `systemctl`, `journalctl` 대신 `docker logs`, `docker exec`, `kubectl logs` 등을 함께 사용한다.

### ③ 웹 서버와 소켓

#### 소켓이란

네트워크로 데이터를 주고받기 위한 통신 인터페이스다. 예를 들어 FastAPI 서버를 다음과 같이 실행하면 TCP 포트 8000에서 연결을 기다린다.

```bash
uvicorn main:app --host 0.0.0.0 --port 8000
```

```
클라이언트
    |  TCP 연결 요청
    v
서버 IP:8000
    v
TCP 소켓
    v
Uvicorn
    v
FastAPI 애플리케이션
    v
응답 반환
```

구분해야 할 개념:

- **리스닝 소켓**: 새로운 TCP 연결을 기다리는 소켓
- **연결된 소켓**: 특정 클라이언트와의 통신에 사용되는 소켓
- **파일 디스크립터**: 리눅스에서 소켓 등 자원을 참조하는 정수형 식별자
- **포트**: 서비스를 구분하는 번호 (소켓 = 포트가 아니다)
- **TCP 연결 상태**: ESTABLISHED, TIME_WAIT, CLOSE_WAIT 등

#### 반드시 알아야 하는 TCP 상태

| 상태 | 의미 | 확인할 내용 |
|---|---|---|
| LISTEN | 연결 요청을 기다림 | 서버가 포트를 열고 있는가? |
| SYN-SENT | 연결 요청을 보냄 | 상대방의 응답이 도착하는가? |
| SYN-RECEIVED | 연결 요청을 받고 응답함 | 연결 설정이 완료되는가? |
| ESTABLISHED | 연결 성립 | 연결이 정상적으로 유지되는가? |
| FIN-WAIT-1 | 연결 종료 절차 첫 단계 | 종료 요청과 응답이 진행되는가? |
| CLOSE-WAIT | 상대방이 종료를 알림 | 애플리케이션이 소켓을 적절히 닫는가? |
| TIME-WAIT | 종료 후 일정 시간 대기 | 정상 종료인지, 연결량이 과도한지 |

```bash
# 현재 TCP 연결 상태 확인
ss -ant
# CLOSE_WAIT 연결 개수
ss -ant state close-wait | wc -l
# TIME_WAIT 연결 개수
ss -ant state time-wait | wc -l
# 특정 포트의 연결 확인
sudo ss -antp '( sport = :8000 )'
```

- **TIME_WAIT**가 많다고 무조건 문제는 아니다. 정상 종료에서도 발생한다.
- **CLOSE_WAIT**가 계속 증가하고 줄지 않으면 애플리케이션의 자원 정리 문제를 의심한다. 단, 존재만으로 버그라고 단정하지 않는다.
- 연결 상태와 함께 요청량, 오류율, 파일 디스크립터 사용량, 애플리케이션 로그를 확인한다.

#### 502와 504 구분

- **502 Bad Gateway**: 프록시가 업스트림 서버에서 유효한 응답을 받지 못했을 때
- **504 Gateway Timeout**: 프록시가 업스트림 응답을 정해진 시간 안에 받지 못했을 때
- 둘 다 원인이 다양하므로 상태 코드만으로 원인을 단정하지 않는다.

### ④ 데이터베이스와 캐시

#### 핵심 개념

| 개념 | 의미 |
|---|---|
| Cache Hit | 캐시에서 필요한 데이터를 찾음 |
| Cache Miss | 캐시에 데이터가 없어 원본 저장소에 접근함 |
| TTL | 캐시 데이터의 유효 기간 |
| Cache Invalidation | 캐시 데이터를 무효화하는 작업 |
| Cache Stampede | 만료된 캐시를 재생성하려는 요청이 한꺼번에 몰리는 현상 |
| Cache Penetration | 캐시에 없는 데이터에 대한 반복 요청으로 원본 저장소에 부하 발생 |
| Cache Breakdown | 인기 있는 단일 키 만료 등으로 원본 저장소에 부하 집중 |
| Connection Pool | DB 연결을 재사용하기 위한 연결 풀 |

#### 구조 비교

```
[캐시 미적용]                [캐시 적용]
클라이언트                    클라이언트
    v                            v
FastAPI                      FastAPI
    v                            v
PostgreSQL                   Redis
                                 +-- Cache Hit  --> 응답
                                 +-- Cache Miss --> PostgreSQL
```

#### 측정 항목

평균 응답 시간, p95 응답 시간, 초당 처리량, DB 쿼리 수, 캐시 적중률

#### Cache Stampede 완화 방법

- 캐시 재생성 요청을 하나로 제한하는 Singleflight 방식
- TTL에 무작위 변동(jitter) 추가
- 사전 캐시 갱신
- 요청 병합
- 적절한 캐시 만료 정책

#### DB 연결 고갈 시 확인 순서

무조건 DB의 최대 연결 수를 늘리지 않는다.

1. 연결이 적절히 반환되는가?
2. 쿼리 실행 시간이 지나치게 길지 않은가?
3. 커넥션 풀 크기가 적절한가?
4. 애플리케이션 인스턴스 수에 비해 전체 연결 수가 과도하지 않은가?
5. DB 자체가 처리할 수 있는 부하를 초과했는가?

> 예: 애플리케이션 인스턴스 4개가 각각 최대 20개의 연결을 쓰면, 다른 사용자를 제외하고도 최대 80개의 연결이 필요할 수 있다.

## 4. 실습 예제

첫 실습 환경은 **FastAPI + Nginx + k6 + 리눅스 모니터링** 조합을 권장한다. 이 환경 하나로 연결 오류, 타임아웃, CPU 과부하, 502·504, 동시 요청 처리를 단계적으로 실습할 수 있다.

### 실습 도구

| 도구 | 역할 |
|---|---|
| FastAPI | 테스트용 웹 서버 |
| Docker | 서버 실행 환경 구성 |
| k6 | 동시 요청과 부하 생성 |
| top | CPU 및 프로세스 확인 |
| vmstat | 메모리와 시스템 상태 확인 |
| ss | TCP 소켓 상태 확인 |
| curl | HTTP 응답 및 지연 확인 |

### 실습 1. CPU 과부하

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/normal")
def normal():
    return {"message": "ok"}


@app.get("/slow")
def slow():
    total = 0
    for i in range(20_000_000):
        total += i
    return {"result": total}
```

```bash
uvicorn main:app --host 0.0.0.0 --port 8000
# 다른 터미널에서
top
```

관찰할 것:

1. `/normal`의 응답 시간은 어떻게 변하는가?
2. `/slow` 요청이 증가하면 CPU 사용률은 어떻게 변하는가?
3. 요청 수가 증가할 때 오류율은 어떻게 변하는가?
4. 요청이 끝난 뒤 CPU 사용량은 정상으로 돌아오는가?

학습 개념: CPU 병목, 동시 요청 처리, 애플리케이션 워커, 요청 대기 시간, 처리량(Throughput), 지연 시간(Latency)

> 실제 서비스에서는 연산 최적화, 작업 큐 분리, 워커 구성, 수평 확장 등을 상황에 따라 검토한다.

### 실습 2. 서버 타임아웃

```python
import time
from fastapi import FastAPI

app = FastAPI()


@app.get("/timeout")
def timeout():
    time.sleep(10)
    return {"message": "completed"}
```

```bash
curl -v --max-time 3 http://localhost:8000/timeout
```

클라이언트가 3초만 기다리므로 클라이언트 측 타임아웃이 발생한다. **클라이언트 타임아웃이 발생해도 서버 작업이 자동으로 취소되는 것은 아니다.** 실제 동작은 프레임워크와 요청 처리 방식에 따라 다르다.

생각해 볼 질문:

- 클라이언트 타임아웃과 서버 타임아웃은 어떻게 다른가?
- 로드 밸런서의 유휴 제한 시간과 애플리케이션 처리 시간은 어떤 관계인가?
- 서버 응답이 느려지면 대기 중인 요청은 어떻게 되는가?
- 타임아웃을 늘리는 것이 항상 올바른 해결책인가? → 원인을 해결하지 않고 늘리면 연결과 작업이 오래 유지되어 자원 부족이 더 심해질 수 있다.

### 실습 3. 소켓 및 연결 수 증가

```bash
sudo ss -lntp   # 리스닝 소켓
ss -ant         # 전체 TCP 연결 상태
ss -s           # 소켓 통계
ulimit -n       # 파일 디스크립터 한도
```

학습 개념: 소켓 수와 파일 디스크립터, 리스닝 큐와 연결 대기, 동시 연결 수, 연결 재사용, 연결 종료, 파일 디스크립터 한도

> 동시 연결이 많다는 사실만으로 장애가 발생하지는 않는다. 처리 능력, 연결 유지 시간, 메모리, 애플리케이션 구조를 함께 고려한다.

### 실습 A. 캐시 적용 전후 비교

같은 데이터를 반복 조회하며 평균·p95 응답 시간, 처리량, DB 쿼리 수, 캐시 적중률을 비교한다.

### 실습 B. 캐시 만료로 인한 부하 집중

1. 인기 게시글 조회 결과를 Redis에 저장한다.
2. 해당 캐시의 TTL이 만료된다.
3. 여러 요청이 동시에 들어온다.
4. 다수의 요청이 PostgreSQL로 전달된다.
5. DB의 CPU 사용량과 응답 시간이 증가한다.

### 실습 C. DB 연결 고갈

동시 요청이 늘고 쿼리가 오래 걸리면 연결이 반환되지 않고 점유된다. 다음 현상을 관찰한다.

- 커넥션 풀 대기 시간 증가
- DB 연결 수 증가
- API 응답 지연
- 연결 획득 타임아웃
- DB 최대 연결 수 도달
